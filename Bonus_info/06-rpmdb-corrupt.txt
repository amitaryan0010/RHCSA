
RPM Database Management

Command	            Description
rpm --rebuilddb	    Rebuild the RPM database (if corrupted)
rpm --initdb	    Initialize a new RPM database
rpm --import	    Import a GPG key
rpm --checksig	    Verify package signature

The RPM database is stored at:
    # /var/lib/rpm/ 
    -rw-r--r-- 1 root root 8.0M Jul 20 05:30 Packages
    -rw-r--r-- 1 root root 1.2M Jul 20 05:30 Name
    -rw-r--r-- 1 root root 512K Jul 20 05:30 Basenames
    -rw-r--r-- 1 root root 256K Jul 20 05:30 Requirename
    -rw-r--r-- 1 root root 128K Jul 20 05:30 Providename
    (The main file is Packages — this is the BerkeleyDB database that holds all package metadata.)

    # ls -lh /var/lib/rpm/
    total 136M
    -rw-r--r--. 1 root root 113M Jul 20 11:19 rpmdb.sqlite
    -rw-r--r--. 1 root root  32K Jul 20 11:19 rpmdb.sqlite-shm
    -rw-r--r--. 1 root root    0 Jul 20 11:19 rpmdb.sqlite-wal

    (RHEL 9 RPM Database — SQLite Format Explained. Your system is using the newer SQLite-based RPM database (not the old BerkeleyDB format))
    Understanding the Three SQLite Files
    File	                Size	    Purpose
    rpmdb.sqlite	        113M	    Main database file with all package metadata
    rpmdb.sqlite-shm	    32K	        Shared memory for concurrent access, Allows multiple processes to access the database safely, Prevents conflicts when rpm, yum, dnf run together
    rpmdb.sqlite-wal	    0 bytes	    Write-ahead log for crash recovery, Ensures crash recovery (if power fails during write), Empty when database is idle

--------------------------------------------------
Common Causes of RPM DB Corruption
⚡ Power failure during rpm/yum/dnf install
🔴 Killed process (Ctrl+C) during installation
💾 Disk full during package operation
🔒 Stale lock files (__db.00x files)
🐛 Multiple concurrent rpm commands running simultaneously

---------------------------------------------------
How Corruption Looks — Real Error Messages

Scenario 1: Running rpm -qa on a corrupted DB
    # rpm -qa
    Corrupted Output:   
        error: rpmdb: BDB0113 Thread/process 12453/140234567890 failed: BDB1507 Thread died in Berkeley DB library
        error: error(-30973) getting records from Packages
        error: cannot open Packages index using db4 - (-30973)
        error: cannot open Packages database in /var/lib/rpm

Scenario 2: Running yum install or dnf install
    # dnf install httpd
    Corrupted Output:
        Error: Failed to read RPM database
        error: db4 error(11) from dbenv->open: Resource temporarily unavailable
        error: cannot open Packages database in /var/lib/rpm
        Traceback (most recent call last):
        File "/usr/lib/python3.6/site-packages/dnf/base.py", line 233, in fill_sack
            self._sack.load_system_repo(mdtype)
        libdnf.error.LibrepoError: can't open RPM database

Scenario 3: Stale lock files present
    # rpm -q httpd
    Output:
        error: rpmdb: BDB0060 PANIC: fatal region error detected; run recovery
        error: db4 error(-30973) from dbenv->open: DB_RUNRECOVERY: Fatal error, run database recovery
        error: cannot open Packages index using db4 - (-30973)
        error: cannot open Packages database in /var/lib/rpm    

Scenario 4: During a yum update
    # yum update
    Output:
        error: rpmdb open failed
        CRITICAL:yum.main:
        Error: rpmdb open failed

Scenario 5: Lock file blocking
    # rpm -ivh package.rpm
    Output:
        error: can't create transaction lock on /var/lib/rpm/.rpm.lock (Resource temporarily unavailable)

Safe Fix — Step by Step (RHEL 8)

✅ Step 1: Check if any rpm/yum/dnf is still running
    # ps aux | grep -E 'rpm|yum|dnf' | grep -v grep
    Output (if stale process):
        root      12453  0.0  0.1  12345  1234 ?  Ds  05:30  0:00 rpm -ivh package.rpm
    If you see a zombie or stuck process, kill it:
        # kill -9 12453

✅ Step 2: Check and remove stale lock files
    # ls -lh /var/lib/rpm/__db*
    Output:
        -rw-r--r-- 1 root root 16K Jul 20 05:30 /var/lib/rpm/__db.001
        -rw-r--r-- 1 root root 16K Jul 20 05:30 /var/lib/rpm/__db.002
        -rw-r--r-- 1 root root 16K Jul 20 05:30 /var/lib/rpm/__db.003
    Remove them:
    # rm -f /var/lib/rpm/__db*

✅ Step 3: Backup the RPM database (VERY IMPORTANT)
    # cp -a /var/lib/rpm /var/lib/rpm.backup_$(date +%Y%m%d_%H%M%S)
    Verify backup:
    # ls -lh /var/lib/ | grep rpm
    Output:
        drwxr-xr-x 2 root root 4.0K Jul 20 05:30 rpm
        drwxr-xr-x 2 root root 4.0K Jul 20 05:30 rpm.backup_20250720_053044

✅ Step 4: Rebuild the RPM database
    # rpm --rebuilddb
    Output (with verbose flag for more detail):
    # rpm -vv --rebuilddb
        D: rebuilding database /var/lib/rpm into /var/lib/rpmrebuilddb.12345
        D: opening old database with dbapi 3
        D: opening new database with dbapi 3
        D: reading old database headers, writing to new database
        D: replacing old database with new database
        D: removing old database files
        D: rename /var/lib/rpmrebuilddb.12345 to /var/lib/rpm

✅ Step 5: Verify the fix
    # rpm -qa | head -2
    Expected Good Output:
        basesystem-11-13.el9.noarch
        bash-5.1.8-6.el9.x86_64
        ✅ No errors = database is fixed!

✅ Step 6: Test dnf/yum as well
    # dnf check
    Good Output:
        Last metadata expiration check: 0:05:43 ago on Sun 20 Jul 2025 05:25:01 AM UTC.

Fixing a Corrupted SQLite Database (RHEL 9)
If corruption occurs, the process is different from old BerkeleyDB:

✅ Step 1: Backup the database
    # cp -a /var/lib/rpm /var/lib/rpm.backup_$(date +%Y%m%d_%H%M%S)

✅ Step 2: Remove shared memory and WAL files
    # rm -f /var/lib/rpm/rpmdb.sqlite-shm
    # rm -f /var/lib/rpm/rpmdb.sqlite-wal

✅ Step 3: Rebuild the database
    # rpm --rebuilddb
        (no output = success)

✅ Step 4: Verify
    # rpm -qa | wc -l
        Note: In RHEL 9+, --rebuilddb is much faster and safer than RHEL 8 because SQLite handles crash recovery automatically.

✅ Stale Lock Files — SQLite Version
In SQLite, there are no __db.00x files, but you might see:
    # ls -lh /var/lib/rpm/
        If rpmdb.sqlite-shm stays large (> 64K) for a long time, it might mean:

    A process is holding a lock
    OR 
    the system crashed with an open transaction
    Fix:
        # rm -f /var/lib/rpm/rpmdb.sqlite-shm
        # rpm --rebuilddb

------------------------------------------------------
If only one package corrupted then we can download the same package and update the DB with 'justdb' flag:
Understanding --justdb Flag
    This is the critical flag for your situation:
    # rpm -i --justdb --nodeps --force package.rpm

    (--justdb	Only update the database — do NOT touch files on disk)
    (💡 Without --justdb, rpm would try to copy files again — but the files are already there!)
-----------------------------------------------------
"rpm --initdb" : When to Use?
    # rpm --initdb      --> creates a fresh empty database.

⚠️ Use this only on a new/blank system where no packages are installed yet. Using it on a production system wipes all package records.
