to check the mac address table or routing table:
Both commands show the ARP (Address Resolution Protocol) cache — the mapping between IP addresses and MAC addresses on your local network. This is how your machine knows which hardware address to send packets to on the same network segment.

    # arp -n 
    [root@rhel-9 local-repo]# arp -n
    Address                  HWtype  HWaddress           Flags Mask            Iface
    192.168.139.1            ether   0a:00:27:00:00:05   C                     eth1
    10.51.167.97                     (incomplete)                              eth0
    192.168.139.2            ether   08:00:27:70:2a:7f   C                     eth1
    192.168.0.1              ether   04:95:e6:22:36:50   C                     eth0

    Column	        Meaning
    Address	IP      address of the neighbor
    HWtype	        Hardware type (ether = Ethernet)
    HWaddress	    MAC address (hardware address)
    Flags	        Status flags (C = Complete/Valid)
    Iface	        Network interface this entry belongs to

    OR

    [root@rhel-9 local-repo]# ip neigh
    192.168.139.1 dev eth1 lladdr 0a:00:27:00:00:05 REACHABLE
    10.51.167.97 dev eth0 FAILED
    192.168.139.2 dev eth1 lladdr 08:00:27:70:2a:7f STALE
    192.168.0.1 dev eth0 lladdr 04:95:e6:22:36:50 REACHABLE

    Column	        Meaning
    IP	            Neighbor IP address
    dev	            Interface
    lladdr	        Link-layer (MAC) address
    State	        Current connection state (most important column)

    ARP Neighbor States Explained
    State	    Meaning	                        Can Send Packets?	        Action Taken
    REACHABLE	Recently confirmed	            ✅ Yes	                Use immediately
    STALE	    Old but not expired	            ✅ Yes (will refresh)	Use, then refresh
    DELAY	    Waiting for confirmation	    ✅ Yes	                Short delay before refresh
    PROBE	    Actively refreshing	            ✅ Yes	                Sending ARP probes
    FAILED	    Resolution failed	            ❌ No	                Cannot reach this neighbor
    INCOMPLETE	ARP request sent, no reply	    ❌ No	                Waiting for reply
    NOARP	    No ARP needed	                ✅ Yes	                Special cases

**TCP States:
    TCP States represent the lifecycle of a connection (from LISTEN to CLOSED).
    LISTEN = Server waiting for connections.
    ESTAB = Connection is active and working.
    SYN_SENT/SYN_RECV = Connection in progress (handshake phase).
    FIN_WAIT1/FIN_WAIT2/CLOSING/LAST_ACK = Connection closing.
    TIME_WAIT = Connection closed, waiting for timeout (normal).
    CLOSE_WAIT = Remote closed, but local app hasn’t (common issue).
    UDP States are simpler:
        UNCONN = Server waiting for datagrams.
        ESTAB = Active UDP communication (kernel tracks it).

with NMCLI Command

nmcli is the command-line tool for NetworkManager on RHEL and other Linux systems. You can use it to view, create, modify, activate, and troubleshoot network connections without using the GUI. Common things you can do
    - See network status
        nmcli general status
        nmcli device status
        nmcli connection show
    - Show IP details
        nmcli device show eth0
    - Bring a connection up or down
        nmcli connection up <name>
        nmcli connection down <name>
    - Configure IP settings
        Set static IP, gateway, DNS, and routes
        Switch between DHCP and manual configuration
    - Manage Ethernet interfaces
        Assign IPs
        Change auto-connect settings
        Set interface priority and metrics
    - roubleshoot
        Check whether a device is connected
        See which DNS/gateway is in use
        Verify if a connection is active
Useful examples

- Adding a new profile/connection
    # nmcli con add type ethernet con-name 'ens192' ifname ens192
    # nmcli con modify "ens192" ipv4.addresses 192.168.122.49/24 ipv4.gateway 192.168.122.1 ipv4.method manual
    # nmcli con up ens192

- View Connection Details
    # nmcli connection show eth0

- Adding DNS
    # nmcli connection modify eth0 ipv4.dns "192.168.0.1 8.8.8.8"

- Adding routing
    ** Simple static routes only then you can just add routes in the main table:
            # nmcli con modify ens192 +ipv4.routes "192.168.122.13/32 192.168.122.1"
            # nmcli con modify ens192 +ipv4.routes "192.168.122.14/32 192.168.122.1"
            # nmcli con modify ens192 +ipv4.routes "192.168.122.15/32 192.168.122.254"
            # nmcli dev reapply ens192

            If rules need to apply
            # nmcli con modify "ens192" ipv4.routing-rules "priority 200 iif ens192"

    ** policy-based routing 
        - If we need a custom routing table + rule only when you want special routing behavior such as:
            traffic coming from a specific interface
            traffic from a specific source IP
            different routes for the same destination depending on policy

            # /etc/iproute2/rt_tables (custom tables)
                400 nexus-nic 
                (This gives table 400 a friendly name. Note: the name is optional. Linux can use table 400 even without a name, but naming it makes troubleshooting easier.)

            # nmcli con modify ens192 +ipv4.routes "192.168.122.13/32 192.168.122.1 table=400"
            # nmcli con modify ens192 +ipv4.routes "192.168.122.14/32 192.168.122.1 table=400"
            # nmcli con modify ens192 +ipv4.routes "192.168.122.15/32 192.168.122.1 table=400"
                (This puts those routes into routing table 400, not the main table.)

            # nmcli con modify ens192 ipv4.routing-rules "priority 100 iif ens192 table 400"
            (Add a routing rule: This is the part that decides when table 400 should be used.)

            # nmcli con reload
            # nmcli dev reapply ens192

            # ip rule list (will list custom table if any)
            # ip route show table 400
            # ip route show table main

- change priority
    # nmcli con modify ens192 ipv4.route-metric 100
    # nmcli con reload
    # nmcli dev reapply ens192

RHEL example with 2 NICs and policy routing

Here’s a practical example using two interfaces:
    ens192 → 192.168.122.50/24, gateway 192.168.122.1
    ens224 → 10.10.10.50/24, gateway 10.10.10.1

Assume you want:
        traffic from 192.168.122.50 to go out via ens192
        traffic from 10.10.10.50 to go out via ens224
        keep the routes separated using custom tables

What to put in /etc/iproute2/rt_tables
        100 ens192_table
        200 ens224_table

Configure routes in each table
        nmcli con modify ens192 +ipv4.routes "default via 192.168.122.1 table=100"
        nmcli con modify ens192 +ipv4.routes "192.168.122.0/24 dev ens192 table=100"

        nmcli con modify ens224 +ipv4.routes "default via 10.10.10.1 table=200"
        nmcli con modify ens224 +ipv4.routes "10.10.10.0/24 dev ens224 table=200"

Add routing rules
        nmcli con modify ens192 ipv4.routing-rules "priority 100 from 192.168.122.50/32 table 100"
        nmcli con modify ens224 ipv4.routing-rules "priority 200 from 10.10.10.50/32 table 200"

Apply the changes
        nmcli dev reapply ens192
        nmcli dev reapply ens224
    if needed:
        nmcli con down ens192
        nmcli con up ens192
        nmcli con down ens224
        nmcli con up ens224

Verify
        ip rule list
        ip route show table 100
        ip route show table 200
        ip route show table main

When to use iif
    Use iif ens192 only if you want packets arriving on ens192 to use a specific table:
        nmcli con modify ens192 ipv4.routing-rules "priority 150 iif ens192 table 100"
