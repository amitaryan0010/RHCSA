** Main configuration for YUM/DNF package manager
    --> On RHEL 9, yum is actually a compatibility wrapper for dnf. When you run yum, it internally calls dnf. However, the configuration file /etc/yum.conf is still used.

The History: Why Two Files?
    YUM (Yellow dog Updater, Modified) — The Old Way
        Created: Early 2000s
        Default on: RHEL 5, 6, 7
        Language: Python 2
        Config file: /etc/yum.conf
        Status: Deprecated (but still works for compatibility)
    DNF (Dandified YUM) — The New Way
        Created: 2015
        Introduced on: RHEL 8+
        Language: Python 3
        Config file: /etc/dnf/dnf.conf
        Status: ✅ Official replacement for YUM on RHEL 8 and later
        Why created: YUM was slow, had dependency resolution issues, lacked features

----------------------------------------
On RHEL 9 — What Actually Happens?

When you run yum on RHEL 9:
    # which yum
    /usr/bin/yum

    # ls -lh /usr/bin/yum
    lrwxrwxrwx. 1 root root 5 Apr 15 10:30 /usr/bin/yum -> dnf-3
    
    # file /usr/bin/yum
    /usr/bin/yum: symbolic link to /etc/alternatives/yum

What's really happening:
    User runs "yum"
            ↓
    /usr/bin/yum is a symlink
            ↓
    Actually calls DNF internally
            ↓
    DNF reads configuration from /etc/dnf/dnf.conf
            ↓
    Also checks /etc/yum.conf for backward compatibility

So on RHEL 9:
    ✅ yum command still works (for backward compatibility)
    ✅ It internally uses DNF
    ✅ Configuration is read from /etc/dnf/dnf.conf (primary)
    ⚠️ /etc/yum.conf is also read (for old scripts/tools that expect it)

File Locations and Hierarchy
    Configuration File Locations:
        /etc/dnf/dnf.conf          ← PRIMARY config (DNF reads this first)
        /etc/yum.conf              ← LEGACY config (read for compatibility)
        /etc/dnf/plugins/          ← Plugin configurations
        /etc/yum.repos.d/          ← Repository definitions (.repo files)
        /etc/dnf/vars/             ← Variable definitions (like $releasever)

Repository Files:
    Both YUM and DNF read from the same repository directory:
        # ls /etc/yum.repos.d/

Settings in /etc/dnf/dnf.conf take priority over /etc/yum.conf.

---------------------------------------------------
Recommended /etc/yum.conf for RHEL 9; Here’s a clean and practical configuration:

    [main]
    cachedir=/var/cache/yum
    keepcache=0
    debuglevel=2
    logfile=/var/log/yum.log
    exactarch=1
    obsoletes=1

    gpgcheck=1
    installonly_limit=3
    clean_requirements_on_remove=True
    best=True
    skip_if_unavailable=False

Each .conf file in /etc/dnf/plugins/ controls a specific plugin's behavior. These plugins extend DNF's functionality beyond basic package management.
1) copr.conf — COPR (Community Projects Repository)
    What it does:
        Manages access to COPR (Fedora Community Projects Repository)
        COPR allows third-party developers to build and distribute RPM packages
        Similar to PPA (Personal Package Archive) in Ubuntu

    # cat /etc/dnf/plugins/copr.conf
    [fedora]
    hostname = copr.fedorainfracloud.org
    protocol = https
    port = 443

    # To add another Copr hub, make a new section with its hostname, protocol and port.
    # (protocol and port are optional and their default values are `https` and `443` respectively).
    # [name-of-hub]
    # hostname = hub-hostname
    # protocol = https (optional)
    # port = 443 (optional)

    When to use:
        Installing packages from community developers (e.g., newer versions not in official repos)
        ⚠️ Use with caution — COPR packages are community-maintained, not officially supported by Red Hat

2) debuginfo-install.conf — Debuginfo Plugin
    What it does:
        Automatically installs debug symbols for packages when needed
        Used for debugging crashes or analyzing performance

    cat /etc/dnf/plugins/debuginfo-install.conf
    [main]
    enabled=1
    autoupdate=0

    When to use:
        - Install a package WITH its debug symbols
            # dnf debuginfo-install httpd
                * This will install:
                    - httpd (main package)
                    - httpd-debuginfo (debug symbols)
        - Real-world scenario:
            * A service crashes and you need to analyze the core dump
            * You need to run gdb (GNU Debugger) on a binary
            * You're performance profiling an application

3) product-id.conf — Product ID Plugin
    What it does:
        Manages RHEL product identification information
        Part of Red Hat subscription management
        Stores which RHEL product you're running

    #  cat /etc/dnf/plugins/product-id.conf
        [main]
        enabled=1

    What it manages:
        - View your product ID
            # cat /etc/rhsm/facts/product_id.json
        - View installed product certs
            # ls /etc/pki/product/
        - Real-world scenario:
            * Red Hat needs to know which RHEL product you have (RHEL Server, RHEL Workstation, etc.)
            * Used for subscription management
            * Ensures you have access to the correct repositories

4) subscription-manager.conf — Subscription Manager Plugin
    What it does:
        Manages your Red Hat subscription status
        Controls access to entitled repositories
        Validates your subscription with Red Hat

    # cat /etc/dnf/plugins/subscription-manager.conf
        [main]
        enabled=1

        # When following option is set to 1, then all repositories defined outside redhat.repo will be disabled
        # every time subscription-manager plugin is triggered by dnf or yum
        disable_system_repos=0        

    - Real-world scenario:
        * You have a Red Hat subscription (paid or trial)
        * You need access to RHEL security updates and patches
        * Red Hat needs to verify your subscription is valid

.repo files are repository configuration files used by DNF (and its predecessor, YUM) to define where to download RPM packages from. These files tell your system:

Where to find packages (URLs)
How to verify their authenticity (GPG keys, SSL certificates)
Which packages to include or exclude
How often to refresh metadata


🔧      Common Directives in .repo Files
    Here’s a complete list of the most important directives you can use in .repo files:

    📌 Core Directives (Required or Common)

        Directive			Values					Description										Example
        [repository-id]		Any unique name			Unique identifier for the repository			[epel]
        name				Any string				Human-readable name for the repository			name=EPEL 9
        baseurl				URL						Base URL where packages are stored				baseurl=https://example.com/repo
        enabled				0 or 1					Enable/disable the repository					enabled=1
        gpgcheck			0 or 1					Verify GPG signatures of packages				gpgcheck=1
        gpgkey				File path or URL		Path to GPG key for signature verification		gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-epel-9

        🔒 Security Directives
        repo_gpgcheck		0 or 1					Verify GPG signature of repository metadata		repo_gpgcheck=0
        sslverify			0 or 1					Verify SSL certificate of the repository		sslverify=1
        sslcacert			File path				Path to CA certificate for SSL verification		sslcacert=/etc/rhsm/ca/redhat-uep.pem
        sslclientcert		File path				Path to client certificate for authentication	sslclientcert=/etc/pki/entitlement/123456789.pem
        sslclientkey		File path				Path to client private key for authentication	sslclientkey=/etc/pki/entitlement/123456789-key.pem
        sslverifystatus		0 or 1					Check certificate revocation status (OCSP)		sslverifystatus=1

        ⏱️ Performance & Caching Directives
        metadata_expire		Seconds or time string	How long to cache repository metadata			metadata_expire=86400 (24 hours)
        enabled_metadata	0 or 1					Download metadata for disabled repos			enabled_metadata=0
        retries				Number					Number of retries for failed downloads			retries=5
        timeout				Seconds					Timeout for downloads							timeout=30		

        📦 Package Filtering Directives
        exclude				Package names			Exclude specific packages from this repo		exclude=package1 package2
        includepkgs			Package names			Include only specific packages from this repo	includepkgs=package1 package2
        module_hotfixes		0 or 1					Allow module overrides							module_hotfixes=0

        🌐 Network Directives
        proxy				URL						HTTP/HTTPS proxy for downloads					proxy=http://proxy.example.com:8080
        proxy_username		String					Username for proxy authentication				proxy_username=user
        proxy_password		String					Password for proxy authentication				proxy_password=pass

🛠️ How .repo Files Work
    Step-by-Step: How DNF Uses .repo Files
    DNF reads all .repo files in /etc/yum.repos.d/.
    Parses each repository section (e.g., [epel]).
    Checks if the repo is enabled (enabled=1).
    Downloads repository metadata (package lists, versions, dependencies).
    Verifies metadata (GPG signatures, SSL certificates).
    Caches metadata (for metadata_expire duration).
    Allows package installation from the repo.


📝 How to Create a Custom .repo File
    1: Create a New .repo File
        # sudo nano /etc/yum.repos.d/custom.repo
        # Add Repository Definition
            [my-custom-repo]
            name=My Custom Repository
            baseurl=https://example.com/path/to/repo
            enabled=1
            gpgcheck=1
            gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-custom

        # Save and Test
            - dnf repolist

    2: We can create the local repo as well, copy the rpm files to a directory and then create the repodata using crearerepo command:

        # dnf download bash-completion htop java-11-openjdk --destdir=/root/local-repo (or copy from another source)
