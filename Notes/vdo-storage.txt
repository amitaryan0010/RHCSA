VDO (Virtual Data Optimizer) 
    is a data efficiency technology in Linux, developed by Red Hat, that provides inline deduplication, compression, and thin provisioning at the block device level.While Stratis optimizes the management of storage pools, VDO optimizes the capacity of storage pools by reducing the physical footprint of redundant data before it is written to disk.

The Three Layers of VDO Efficiency
    When data is written to a VDO volume, it passes through three optimization phases in real time:
        - Zero-Block Elimination: VDO filters out blocks that contain only zeros. These blocks are recorded in metadata but consume no space on disk.
        - Inline Deduplication: VDO analyzes incoming data blocks for identical content using a high-performance index. If a duplicate block is found, VDO updates the metadata to point to the existing physical block instead of writing it again.
        - Inline Compression: The remaining unique blocks are compressed using the kvdo kernel module. Multiple compressed blocks are packed together into a single 4 KB physical disk block.

How VDO Integrates with Stratis
    Originally, VDO was managed as a standalone device mapper target (vdo). However, in newer enterprise Linux distributions (like RHEL 9), VDO functionality has been completely integrated into Stratis. When you use Stratis, you do not need to configure VDO manually. Stratis automatically layers and manages VDO underneath its pools to optimize data storage transparently.

Comparing the Core Storage Technologies
    To understand where VDO fits in the modern Linux storage stack, it helps to see how it contrasts with Stratis and LVM:
    
    Technology      Primary                         RoleKey Capabilities
    --------------------------------------------------------------------------------------------------------------------
    LVM             Volume Management               Logical volumes, stripping, mirroring, manual resizing.
    VDO             Data Reduction                  Real-time inline deduplication and hardware-level compression.
    Stratis         Unified Storage Architecture    Automatically combines LVM, XFS, and VDO into an easy CLI interface.

You can create a VDO disk separate from Stratis, but the method depends entirely on your RHEL version.The old, standalone vdo create command-line utility from RHEL 8 is deprecated and no longer available in RHEL 9. Instead, Red Hat fully integrated VDO into LVM (Logical Volume Manager). Managing it through LVM provides the exact same standalone block device optimization (independent of Stratis) while making disk resizing much easier.

Step-by-Step Guide: Creating a Standalone VDO Volume (LVM-VDO)

1. Install the Required Packages
    Ensure you have the LVM management utilities and the kvdo kernel module components installed:
    # dnf install lvm2 kmod-kvdo vdo -y

2. Initialize the Physical Disk and Volume group    
    # pvcreate /dev/sdd
    # vgcreate vdovg /dev/sdd

3. Create the Standalone VDO Volume
    Use lvcreate with the --type vdo flag. This command tells LVM to deploy inline data reduction:
    # lvcreate --type vdo --name vdo-lv --size 4G --virtualsize 20G vdovg
    --size 4G: The actual physical boundary matching your disk.
    --virtualsize 20G: The virtual thin-provisioned presentation size exposed to the OS (representing an expected 5:1 deduplication/compression layout strategy).

4. Format the VDO Disk with a Filesystem
    Format the newly generated VDO device. When formatting an LVM-VDO device with XFS, use the -K flag to prevent immediate block discard operations, which saves initial processing cycles:
    # mkfs.xfs -K /dev/vdovg/vdo-lv

5. Mount the VDO DiskCreate a mount directory and attach the storage device:
    # mkdir /vdo_test
    # mount /dev/vdovg/vdo-lv /vdo_test

    Configuring /etc/fstab for a VDO Disk
        - Retrieve the Device UUID: # lsblk --output=UUID /dev/vdovg/vdo-lv
        - Append the Safe Entry to /etc/fstab: # echo "UUID=2a4b6c8d-1234-5678-abcd-ef1234567890 /vdo_test xfs defaults,x-systemd.requires=lvm2-monitor.service 0 0" >> /etc/fstab
        (x-systemd.requires=lvm2-monitor.service: This critical flag forces systemd to wait for LVM services to fully assemble the VDO volume before it tries to mount /vdo_test)
        -  Verify the Configuration: # systemctl daemon-reload; mount -a; df -h

Auditing and Testing VDO Efficiency
    Once your standalone VDO disk is mounted, you can see compression metrics using standard LVM monitoring commands:
    # lvs -o name,size,data_percent,vdo_saving_percent /dev/vdovg/vdo-lv

Test VDO Deduplication (Copying the same data multiple times)
    Unlike random data streams, copying text files or system logs triggers deduplication immediately:
        1) Copy a large, readable database or a folder of system logs into /vdo_test/.
        2) Check df -h /vdo_test (the OS will show space is filling up).
        3) Make 3 or 4 exact duplicates of that file inside the same folder.
        4) Run the lvs command again. You will observe that the vdo_saving_percent metrics spike upward while the backing physical disk space utilization remains flat.

Scaling an LVM-VDO Volume Later
    LVM-VDO gives you two distinct scaling vectors: growing the Virtual Size (giving the OS more thin-provisioned room) or growing the Physical Size (adding more real disks when the drives are full).
    
    Scenario A: Growing the Virtual Size (More Software Capacity)
        - If your files are compression-heavy and deduplicating well, your virtual space may run low while you still have plenty of raw physical disk space left.To expand the virtual presentation size from 20 GB to 40 GB:
            # lvextend --virtualsize 40G /dev/vdovg/vdo-lv
            # xfs_growfs /vdo_test
            (The xfs_growfs command informs the XFS file system layer to instantly absorb the new virtual boundary without unmounting.)
            
    Scenario B: Growing the Physical Size (More Hardware Storage)
        - If your raw disk blocks are physically full, you must add a new hard drive to the backing volume pool.Add a new physical disk (e.g., /dev/sde) to your Volume Group:
            # pvcreate /dev/sde
            # vgextend vdovg /dev/sde
        - Extend the physical allocation pool of your LVM-VDO volume to consume that new physical space:
            # lvextend --size +4G /dev/vdovg/vdo-lv
            (Note: Because VDO manages its data reduction layers tightly, you cannot use a simple -l +100%FREE flag. You must specify the explicit physical size increment (like +4G).)
