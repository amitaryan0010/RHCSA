Stratis 
    is a local storage management solution developed primarily by Red Hat. It is not a new file system from scratch; instead, it is a volume-managing filesystem (VMF) daemon that runs in user space. It integrates existing, battle-tested Linux technologies—specifically the XFS file system, LVM (Logical Volume Manager), and the device-mapper subsystem—into a single, unified interface.
    The primary purpose of Stratis is to bring advanced, enterprise-grade storage features to users with a fraction of the configuration complexity.

_______________________________________________________________________________________________________________________________________________
Core Concepts of Stratis
    Storage Pools: Stratis abstracts individual block devices (like SSDs, NVMe drives, or partitions) into a shared pool of storage.
    Flexible File Systems: Instead of formatting a rigid partition, you create file systems directly from the storage pool. They dynamically expand and consume space from the pool only as data is added.

Key Features
    Thin Provisioning: Allocates storage virtually, meaning file systems only consume actual physical disk space when files are written, rather than reserving large blocks up front.Snapshots: Creates quick, point-in-time copies of file systems that share data blocks, making them highly efficient for backups and testing.
    Data Integrity & Security: Supports built-in pool encryption through LUKS, integrating seamlessly with TPM2 and Network-Bound Disk Encryption (NBDE).
    Simplicity: Consolidates multiple layers of management (partitioning, volume layout, formatting) into simple, high-level CLI commands.


Architecture
    Stratis operates via a client-server setup:
        stratisd: A background service (daemon) written in Rust that manages the hardware components and exposes a D-Bus API.
        stratis-cli: A command-line utility written in Python that communicates with the daemon to let users execute storage tasks

Install the require package:
    [root@rhel-9 ~]# dnf install stratis-cli stratisd

enable and start the service:
    [root@rhel-9 ~]# systemctl enable --now stratisd

 Add two or more disks to play with:
    [root@rhel-9 ~]# lsblk
    NAME                MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
    sdc                   8:32   0    2G  0 disk
    sdd                   8:48   0    2G  0 disk

create a pool with one disk first and list it:
    [root@rhel-9 ~]# stratis pool create cloud1 /dev/sdc
    (Stratis automatically initialized the disk, formatted it using XFS, and placed it under its management layers. You did not have to manually run fdisk, pvcreate, or vgcreate)

    [root@rhel-9 ~]# stratis pool list
    Name            Total / Used / Free    Properties                                   UUID   Alerts
    cloud1   2 GiB / 524 MiB / 1.49 GiB   ~Ca,~Cr, Op   253afdb3-021c-419b-ab90-2f82cf62b8ce   WS001
    (~Ca — Caching is Not Active: What it means: The Ca flag stands for Cache. Because it has a ~ in front of it, your pool does not have a dedicated caching tier attached.)
    (~Cr — Encryption is Not Active: What it means: The Cr flag stands for Crypto (Encryption). The ~ means your pool data is completely unencrypted.)
    (Op means the pool is Operational. The alert WS001 is a standard warning indicating the pool is small or lacks redundancy, which is expected for a 2 GiB single-disk setup.)

Extend the pool with another disk:
    [root@rhel-9 ~]# stratis pool add-data cloud1 /dev/sdd

    [root@rhel-9 ~]# stratis pool list
    Name            Total / Used / Free    Properties                                   UUID   Alerts
    cloud1   4 GiB / 530 MiB / 3.48 GiB   ~Ca,~Cr, Op   253afdb3-021c-419b-ab90-2f82cf62b8ce

    (use x-systemd.requires=stratisd.service. Because Stratis runs as a user-space service (stratisd), standard Linux mounting happens too early during boot before Stratis can assemble the pool. This flag forces systemd to wait for stratisd to be fully running before it attempts to mount /stratis1, preventing your system from hanging or booting into emergency mode.)

Understanding Thin Provisioning
    Each Stratis filesystem reports a virtual size of 1 TiB, but the actual storage consumption depends on how much data is written. The pool's total physical capacity limits the actual storage available.

    Example:
        Pool size: 50 GiB
        4 filesystems created (each shows 1 TiB)
        Total data written across all filesystems: 30 GiB
        Pool used space: approximately 30 GiB
    
    Important: Monitor pool usage to avoid running out of physical space. If the pool fills completely, Stratis cannot assign more space to filesystems, writes can fail, and applications can lose data.

Setting Filesystem Size Limits
    While Stratis filesystems are thin-provisioned, you can set a size limit:
        # sudo stratis filesystem create --size 10GiB --size-limit 10GiB datapool limited_fs
        (This sets the filesystem size and size limit to 10 GiB.)
