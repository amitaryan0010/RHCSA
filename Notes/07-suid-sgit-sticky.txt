SUID, SGID, and the Sticky Bit are special Linux file permissions that override standard access rules to handle advanced execution and file-sharing scenarios.Normally, when you run a file, it runs with your user privileges. When you create a file, it gets your primary group. These three special bits change that default behavior entirely.

1. SUID (Set User ID)
    * What it does: When an executable file with SUID is run, the process runs with the privileges of the file owner, not the user who executed it.
    * Primary Use Case: Allowing standard users to perform specific tasks that require root privileges without giving them full root access.
    * Real-world Example: The /usr/bin/passwd command. Standard users must be able to modify the /etc/shadow file (which is owned by root) to change their own password. SUID temporarily boosts their privileges to root for that single action.How it looks in ls -l: An s replaces the x in the user/owner column (e.g., -rwsr-xr-x).
    * Numerical Value: 4000

2. SGID (Set Group ID)
    * SGID behaves differently depending on whether it is applied to a file or a directory.
    
    * On an Executable File:
        - What it does: The program runs with the privileges of the file's group owner, rather than the user's primary group.
        - Numerical Value: 2000

    * On a Directory (The Most Common Use Case):
        - What it does: Any new file or subdirectory created inside this folder automatically inherits the group ownership of the parent directory, rather than the primary group of the user who created it.
        - Primary Use Case: Collaborative shared folders. It ensures that a team working in the same directory can always read and modify each other's files because they all share the same group ID.
        - How it looks in ls -l: An s replaces the x in the group column (e.g., drwxr-sr-x).

3. Sticky Bit
    * What it does: When applied to a directory, it prevents users from deleting or renaming files inside it unless they are the explicit owner of that file or the root user.
    * Primary Use Case: Shared public directories where everyone has write access, but you want to stop users from maliciously deleting or altering other people's data.
    * Real-world Example: The /tmp directory. Every user on a Linux system can write temporary files there, but the Sticky Bit ensures userA cannot delete a temporary session file belonging to userB.
    * How it looks in ls -l: A t replaces the x in the "others" column (e.g., drwxrwxrwt).
    * Numerical Value: 1000

** Quick Reference Matrix

Special Permission      Octal Value     Effect on Executable File           Effect on Directory                  Appearance (ls -l)
-----------------------------------------------------------------------------------------------------------------------------------
    SUID                    4             Runs as the file owner                No effect                           -rws------
    SGID                    2             Runs as the file group        New files inherit parent group              ----r-s---
    Sticky Bit              1             No effect                     Only file owners can delete files           -------r-t
    
    
----> Note: If you see a capital letter (S or T), it means the underlying execution bit (x) is missing. A lowercase letter (s or t) means the executable bit is present and active.

DEMO:

** SUID:
    Lets create a show_id binary and then complie it with C (gcc) and set the suid and then run, output shows the REAL UID for the user who runs that binary and Effective UID of running as.

** SGID:   
    Lets create a show_gid binary and then complie it with C (gcc) and set the sgid and then run, output shows the REAL GID for the user who runs that binary and Effective GID of running as group.

** Sticky Bit:
    You can try to create a file with normal user under /tmp directory and then try to delete with another normal user, operation will not be permitted since sticky bit is applied at /tmp directory, only root user can delete it.
